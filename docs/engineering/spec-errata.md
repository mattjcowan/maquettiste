# SPEC errata

Places where `SPEC.md` and the phase 1 contract (`engine-design.md`, the schemas under `schemas/v1/`) disagree on purpose.
Each entry is a proposed change to the SPEC text, so the authority matches what the engine accepts. Until the SPEC is
amended, `engine-design.md` decides, and the decision named in each entry records why.

`tests/Maquettiste.Engine.Tests/Json/SchemaValidationTests.cs` loads the Section 6 and 7 examples verbatim
(`tests/fixtures/spec-examples/verbatim/`) and asserts that they fail only for E1 to E3, so no other drift can hide
behind them.

**Applied (2026-09-29, phase 2 close-out; extended 2026-09-30, phase 3 close-out; extended 2026-10-01 for E39).** E6 to E16
and E39 are amended in `SPEC.md`, each change marked "Errata E<n>" beside the text it amends; E39 was applied in `SPEC.md`
directly on 2026-10-01, at the owner's choice (a re-export of the owner's document keeps it only if that document carries
the same change). E1 to E5 and E17 to E38 are not applied. E1 to E5 correct SPEC text that the engine
already enforces; E17, E18, E20 to E26 are built and are what the engine, the schemas and the editor do (E18, E20 to E23
with generation-ui.md §8, less E22's CLI `pack show`, `explain` and `generate --explain`, E24 with the explicit mapping of round 7, E25 with the preview's scope check, E26 with the database schemas of round 9); E19 (`each
database`) waits for the owner's answer to generation-ui.md §10 Q3 and is not built, so databases stay on selectors
(`select databases`). Until the SPEC text changes, this table is the authority for all of them. They are left for the
owner because `SPEC.md` is exported from the owner's document, and a re-export would drop edits made to the file (and
its diagrams live only in that document): apply them there, then export. The SPEC examples keep failing only for E1 to E3.
E27 to E37 come from
`phase-3-design.md` section 10. They are built (rounds P1 to P6 of that document's section 9, closed by gate 3) and are
what the engine, the schemas, the editor and the example packs do; none is applied in `SPEC.md` yet, and all eleven await
the owner, as E17 to E26 do. E34 retires E3: the schema accepts an entity's `lifecycle` now, and the example's
`/lifecycle` still fails only because of its illustrative id (E1). E38 (2026-10-01) is built with engine-design.md 7.0a and awaits
the owner like the others.

| E26 | Sections 9 and 11, database schemas | Tables, views, sequences, a database's convention package entries and entity mappings name a schema by its id (the schema entry of `database.json`); `defaultSchema` stays a name. A `packages` entry is a package id or `{ "package", "schema" }` and is written as the id when it names no schema (the canonical writer's `x-collapse`). A conventional entity table goes to, in order: its table file's `schema` (an overlay), the entity's mapping `schema`, the schema of the nearest `packages` entry up the package tree that names one, the default schema; junction tables keep the default and child tables follow their owner. MQ4014 (error): a convention entry or an entity mapping names a schema its database does not declare (a relation mapping with `schema` is MQ4009). Four batch operations edit schemas: `add-schema`, `rename-schema` (the default follows; nothing else changes because references are ids), `remove-schema` (refused with MQ4015, listing what lives there, unless `target` names the schema it moves to; the default is refused unless `default` names the new default) and `set-default-schema`; they expand into updates of the database and of the moved tables, views, sequences and mappings, all or nothing, over HTTP (`/api/model/batch`) and MCP (`apply_batch`). Moving a table to another schema is a drop and a create in sql-ddl's migration (the schema diff keys tables by schema and name), not an `ALTER ... SET SCHEMA`. Models without schemas generate byte-identical output | The owner, round 9: PostgreSQL and SQL Server projects use many schemas |

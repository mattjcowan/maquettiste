# Releases

What each version added, newest first. Every version is a tag on the repository, an image
(`mattjcowan/maquettiste:<version>`) and the `Maquettiste.Cli` and `Maquettiste.Engine` packages of the same number. The
[getting started](getting-started.md) page and the [update steps](getting-started.md#updating) say how to move to a new
one.

## 0.22.0 (2026-11-09)

- **Relations with several types at an end, part 2.** A relation mapping can now say, per end, how the team's own tables hold each
  link. Storage stays optional: a team may keep entities and tables as separate models, and a pack can join them its own way. The
  mapping's `ends` entry names exactly one way for an end: `foreignKey` (a key to a table that holds every type's rows),
  `foreignKeys` (a key in each type's table), `types` with `{ entity, foreignKey }` items (a key per type), or `idColumn` with an
  optional `typeColumn` and `referencesColumn` (a type and an id, or an id alone). The engine adds no table, column or check.
- **Several types or any entity at both ends.** Both ends of a two-ended relation may now have several types or be any entity, up to
  any entity at both ends. An n-ary relation still keeps one entity per end. Held in a link table, each end names its own way.
  The editor's form offers the **Type** choice at both ends. The canvas draws one node with a line to each type of either end, and
  **Collapse lines** turns it into one box that lists each end's entries under its role.
- **Fixed values and attribute columns.** `constants` (`{ column, value }`) picks a relation's rows in a link table that several
  relations share. `attributes[].column` names the column of a relation attribute. Both apply to every relation mapping with a designed
  `junctionTable`, a one-type relation too. A mapping that writes neither keeps its bytes.
- **Type codes and binding fields.** An entity binding may write `discriminatorValue`, the entity's type code in that database. The
  code is that value, else the mapping's, else the entity's name. A binding field may map a link's columns as `<endId>`,
  `<endId>.type` and `<endId>.<entityId>`.
- **Rules.** MQ4117 (error: what a mapping names doesn't fit together), MQ4118 (info: what the database can't enforce, with the check
  or unique to copy), MQ4119 (warning: a type code changed since the baseline) and MQ4120 (warning: a mapping states storage and leaves
  a placed type out). MQ4115 stays info and now skips a database whose mapping stores the relation. MQ3041 no longer refuses several
  types at both ends. MQ4116 no longer applies to binding fields; it stays for query fields and query collections. The catalog texts of
  MQ3041, MQ4009, MQ4011, MQ4045, MQ4051, MQ4115 and MQ4116 change.
- **The resolved model.** A relation mapping gains `links`, `constants`, `attributes`, `left_out`, `not_stored` and `type_codes`. A join
  path gains `from_type` and `to_type`, and a join step gains `conditions`. A binding field gains `holds` and `key_of`, and a binding
  gains `discriminator_value`. The database view gains `relationStorage`, with the gaps to copy. `get_binding_drift` names the new fields.
- **Editor.** The relation's **Storage** tab has **Held in** and **Linked by**, with pickers, **Rows of this relation**, the lists
  **Left out** and **Not stored**, and **What the database can't enforce** with **Copy**. Quick fixes: "Remove the key" and "Move it to
  the end's entry" (MQ4009), "Not in this database" and "Open the Storage tab" (MQ4115, MQ4120), "Copy the check" (MQ4118) and "Keep
  the stored code" (MQ4119). A read-only binding's entity is left out of the relation's storage, with no finding.
- **Seeds and pages.** A relation's seed rows into a designed link table now write the mapping's fixed values, and each relation that
  shares the table writes its own keys, in the engine's seed rows and in `sql-ddl`'s seed script. `process-docs` pages now name a right's,
  a trigger point's and a scenario step's link ends by their navigation, else their role; they printed nothing there before ("on links
  through , "), so those pages change.
- **A project that doesn't use it is unchanged:** its files, generated bytes, findings and replays. Three things change for
  everyone: the rule catalog has new entries and longer texts, the schemas of `mapping.json`, `entity.json` and `relation.json` change, and
  the `get_template_context` member lists grow. One invalid file changes its finding: a mapping's `ends` entry with no `foreignKey` now
  reports MQ4009 instead of MQ1002. The `process-docs` fix above changes the pages it touches.
- **Upgrading.** Update the schema copies and the `maquettiste-modeling` skill your repository holds. An older engine refuses the new
  keys, so teams upgrade together.
- **Still waiting.** A link table for each pair of types, one column that points into tables spread over several types, a binding for
  links with its own statements, an engine-made check or column and the "Add to table" button. Seeds and query fields through such an end stay refused (MQ7105, MQ4116).
- **New names, from the design (section 16, part 2) and added while building, confirmed by the owner on 2026-11-09.**
  - Format: in a relation mapping's `ends` entry, `foreignKeys`, `types` (items `{ entity, foreignKey }` or `{ entity, referencesColumn }`,
    schema title "End type storage"), `idColumn`, `typeColumn` and `referencesColumn`; the mapping key `constants` (items
    `{ column, value }`); `attributes[].column` on a relation mapping; the entity binding key `discriminatorValue`; the binding field forms

  - Field names: the field map, Map by name and the drift report name the new fields `<navigation>Type`, `<navigation>Id` and

  - Rules: MQ4117, MQ4118, MQ4119 and MQ4120.
  - Template members: on a relation mapping, `links` (each with `table` and `ends`, each end with `end`, `type`, `is_holder`, `columns`,
    `referenced_table`, `referenced_columns`, `foreign_key`, `type_column`, `codes`), `constants` (`column`, `values`), `attributes`
    (`attribute`, `column`), `left_out` and `not_stored` (`end`, `entity`), `type_codes` (`entity`, `code`); `step.conditions` (`column`,
    `values`), `path.from_type`, `path.to_type`, `navigation.type_joins`, `entity_mapping.type_joins`; on a binding field `holds` and
    `key_of`; on a binding `discriminator_value`.
  - API: `RelationMappingRecord.links`, `.constants`, `.attributes`, `.leftOut`, `.notStored`, `.typeCodes`; `BindingFieldRecord.holds` and
    `.keyOf`; `EntityBindingRecord.discriminatorValue`; `DatabaseView.relationStorage` (`relationId`, `relationName`, `mappingId`, `tables`,
    `leftOut`, `notStored`, `gaps` with `endId`, `kind` and `text`). The gap `kind` is `no-foreign-key`, `shared-table`, `id-only`,
    `type-check`, `count-check`, `one-to-one-unique`, `link-unique`, `per-type-duplicates` or `rows-not-told-apart`. The index format stays `e14`.
  - Editor: Held in, The other end's table, Each type's table, A link table, A table per type, Not in this database,
    Linked by, A key, A column per type, A type and an id, An id unique across types, A key to the shared base table, As written, Refers

    show when the model has no errors.", "Not saved yet: …", "Attribute columns, in the other end's table", "*name* (missing)" for a

  - `process-docs`: the helper `end_name`.

## 0.21.0 (2026-11-08)

- **Relations with several types at an end, part 1.** One end of a two-ended relation may now list several entities and stereotypes
  (`types`, each entry `{ entity }` or `{ stereotype }`), or say `anyEntity: true`. An end writes exactly one of `entity`, `types` or
  `anyEntity`. A Comment can be attached to a Part, an Assembly or a controlled document in one relation, with no shared base entity.
  An entity entry covers that entity and the entities derived from it. A stereotype entry covers every entity that carries it.
  `anyEntity` covers every entity. Role, cardinality, navigation and delete rule stay one per end.
- **Rules.** MQ3041 (an end with several types where it can't be: on an n-ary relation, on both ends of a relation, or `anyEntity` on a
  composition's part end), MQ3042 (a list of one entity: write `entity`, with a quick fix), MQ3043 (an entry another entry covers),
  MQ4115 (info: no database stores such a relation yet) and MQ4116 (a binding field, a query field or a query collection through such a
  relation). The catalog texts of MQ2003, MQ2020, MQ3016, MQ3116, MQ4009, MQ7105, MQ9211, MQ9305 and MQ9604 grow.
- **Guards, sign-off and scenarios.** A guard path through such an end reads what every type holds under one id. `in_state` through it
  is unknown for an object whose type the lifecycle doesn't govern. Unknown is not "no": a guard reading `in_state(...)` or
  `not in_state(...)` is false for that object, and a signature's "Needed when" treats it as needed. Scenario links and connect
  steps are checked against the end's types (MQ9305). Rights, trigger points and freezing work through such an end.
- **The resolved model.** An end gains `types`, `has_several_types`, `stereotypes`, `any_entity` and `common_base`, and a navigation
  gains `targets`. `end.entity` and `navigation.target` are null for such an end and keep their meaning for every other. The
  `typescript` sample writes the union type (`attachedTo?: Part | Assembly`).
- **Editor.** The relation form has a **Type** choice: **One entity**, **Several types** or **Any entity**. The canvas shows bundled
  lines for two types, a junction node for three or more, and a box for a stereotype or any entity. **Collapse lines** and **Expand
  lines** draw one line to a box that lists the types, and back. The choice is saved in the diagram, with the node's position.
- **Nothing is stored yet.** No database stores such a relation. Storage is part 2 (0.22.0), on the team's designed tables with
  explicit mappings. Until then seeds, query fields and binding fields through such an end are refused (MQ7105, MQ4116).
- **A project that doesn't use it is unchanged:** its files, generated bytes, findings and replays. Two things change for everyone: the
  rule catalog has new entries and longer texts, and the model index format is `e14`, so the index is read again once.
- **Upgrading.** The schema copies (`relation.json` and `diagram.json`) and the `maquettiste-modeling` skill change, so update the copies
  your repository holds. An older engine refuses the new keys, so teams upgrade together.
- **Limits.** Only one end of a two-ended relation may have several types. An n-ary relation can't have one, and a composition's part end
  can't be any entity. A stereotype's own attributes are not read through a navigation. There is no per-type cardinality, role or
  navigation, and a right or trigger point can't be narrowed to one type.
- **New names, from the design (section 16) and added while building, confirmed by the owner on 2026-11-08.** From the design: the end keys `types` and `anyEntity`
  and the end type entry `{ entity }` or `{ stereotype }` (schema title "End type"); the rules MQ3041, MQ3042, MQ3043, MQ4115 and MQ4116;
  the template members `end.types`, `end.has_several_types`, `end.stereotypes`, `end.any_entity`, `end.common_base` and
  `navigation.targets`; the API members `EndRecord.types`, `.hasSeveralTypes`, `.stereotypes`, `.anyEntity` and `.commonBase`,
  `NavigationRecord.targets` and `RelationEndSummary.entities`, `.stereotypes`, `.anyEntity` and `.covers`; the index format `e14`;
  the naming key `et:ends`, and `ec:<end id>` for the types of one end (added in the fixes); in the editor, Type, One entity, Several types, Any entity, Stereotypes, Collapse lines, Expand lines,
  "+N not shown", "through *key* (stereotype)" in an entity's related list, such as "through approvable (stereotype)", and "any entity" in a sentence. Added while building:
  - Engine: `RelationEndType`, `EndCoverage`, `RelationEnd.Types`, `.AnyEntity` and `.SingleEntity`, `REnd.OneEntity`.
  - Diagram: `collapsed`, `x` and `y` on a relation's member also hold the lines' toggle and the node's position.
  - Editor: "N entities" and "1 entity" on a stereotype's box, as the explorer counts them, "Any entity" as a box's title, "(stereotype)" after a stereotype's key, the
    tooltips "Only one end may have several types.", "An n-ary relation's ends name one entity each." and "The part end of a composition
    can't be any entity; list the types it may be.", "An end needs at least one type. Choose One entity or Any entity instead.",
    "Add a type to end N", "Remove X from the types", and the quick fixes "Use entity", "Remove the entry" and "Remove *key* (stereotype)". That last button names the stereotype's key, such as "Remove approvable (stereotype)".
  - The `typescript` sample's `nav_type` function.

## 0.20.0 (2026-11-08)

- **Richer sign-off, part 2: rounds, delegation, reminders and a password check.** An approval may now hold **several stages**. Each stage
  has a `round`: stages of one round run side by side, and rounds run one after another. Completing a round never moves the object;
  only the last round's completion does. If a signature completes a round and every later round is skipped or needs nobody, that
  signature makes the move. A stage may carry `when` (**Skip unless**): it is judged when its round starts, and a stage that is skipped
  asks nobody. A rejection clears every round. In the editor, use the Gates tab: **Add stage**, **Round**, **Skip unless**.
- **Delegation.** A signature's `delegateTo` says it may be handed to people who are one of those actors. A signer answers `delegate` and
  names the person. They are finished on that signature, and the object doesn't move. The person it went to answers **on behalf of** the
  delegator, and counts as the delegator's actor. A delegation can't be passed on or go to the delegator themselves, and a rejection ends it. The audit records `delegated`.
- **Reminders and escalation.** A signature's `remindAfter`, `escalateAfter` and `escalateTo` say when to remind and whom to tell. The model
  states them; the running system sends them. An escalation is a notice only and gives no right to sign. Simulation lists the notices a
  time step passes, and a step may expect them (`expect.notices`).
- **Sign again with a password.** A signature's `reauthenticate` asks for the person's identity to be checked again for every response
  on it. The running system does the check. Simulation takes it as done. Generated code refuses a response without it.
- **Scenarios and simulation.** A step may give the response `delegate` with `delegateTo`, and `onBehalfOf` on a later answer. The
  simulation panel shows rounds, skipped stages, delegations and due notices. New rules: MQ8203 (stages out of round order), MQ8204 (a
  malformed reminder or escalation) and MQ8205 (an escalation no later than its reminder); MQ9311 and MQ9305 grow. `route` still does
  nothing.
- **Output.** `csharp-dapper` writes the part 2 code only for a lifecycle that uses it, and `process-docs` shows rounds, delegation and
  notices in its approval tables. A gate whose signatures may be delegated gains `onBehalfOf` and `delegateTo` among its audit fields, so
  outputs that list them (such as an audit table) show the two. In the editor, a signature's **Details** hold **May be delegated to**, **Remind after**, **Escalate
  after**, **Escalate to** and **Sign again with a password**.
- **A project that uses part 1 only, or no approvals, is unchanged:** its files, generated bytes, findings, replays and keys.
- **Upgrading.** Teams upgrade together: an older engine refuses the new keys (a stage's `round` and `when`, a signature's `delegateTo`,
  `remindAfter`, `escalateAfter`, `escalateTo` and `reauthenticate`, a step's `delegateTo` and `onBehalfOf`, `expect.notices`). The schema
  copies and the `maquettiste-modeling` skill change, so update the copies your repository holds. A `csharp-dapper` team that uses part 2:
  - write the stage condition methods `<Gate><Stage>Stage` in `<Process>ApprovalConditions` (answer true when you can't tell);
  - answer `Is<Actor>` for each delegation actor, in `<Process>Handlers.cs`;
  - call `ApprovalNotices.Due` from your scheduler, send the notices, and drop repeats by their id;
  - pass `Reauthenticated` once you have checked the password.

  The pack's README has the steps.
- **New names. Settled by the design (section 14 and decisions 32 to 36), and confirmed by the owner:** a stage's `round` and `when`; a signature's `delegateTo`,
  `remindAfter`, `escalateAfter`, `escalateTo` and `reauthenticate`; a step's `delegateTo` and `onBehalfOf`; the response `delegate`;
  `expect.notices` with the kinds `remind` and `escalate`; the audit outcome `delegated` and the audit record's `onBehalfOf`; the gate
  state's `round` and `skipped`; the trace's `notices`; the rules MQ8203 to MQ8205. In `csharp-dapper`: `SignatureResponse.Delegate`,
  `ProcessEnvelope.DelegateTo`, `.OnBehalfOf` and `.Reauthenticated`, `GateOutcome.Delegated`, `Refusals.GateReauthenticate`,
  `ApprovalNotice` and `ApprovalNotices.Due`, and the stage methods `<Gate><Stage>Stage`. In the editor: Add stage, Round, Skip unless,
  May be delegated to, Remind after, Escalate after, Escalate to, Sign again with a password. Added while building:
  - Engine: `$defs/notice` in the scenario schema, `ExpectedNotice`, `NoticeKind`, `ApprovalNotice(Signature, Kind, Recipients)`, the audit
    record's `delegateTo`, `ApprovalStageState.round` and `.skipped`, `RExpectedNotice`.
  - Templates: `model.approvals_use_rounds`, `_delegation`, `_notices` and `_reauthenticate`; `signature.remind_after_ms` and `_ticks`, and
    `signature.escalate_after_ms` and `_ticks`.
  - `csharp-dapper`: `IApprovalConditions.StageNeeded`; `ApprovalProgress.Round`, `.Skipped`, `.Delegated` and `.Notices`;
    `SignatureEntry.OnBehalfOf` and `.DelegateTo`; `StageDefinition.Round` and `.When`; `SignatureDefinition.RemindAfter`,
    `.EscalateAfter` and `.EscalateTo`; `NoticeKind`; the refusal text `gate-reauthenticate`; `EventRequest.DelegateTo`, `.OnBehalfOf`
    and `.Reauthenticated`; `StepResult.Notices` and `CommandResult.Notices`; the `Is<Actor>` answers for delegation actors.
  - Editor: Details, Round N, Stage, "waits for round N", "Next notice".
- **Limits.** The model keeps no list of absent people and no standing substitutes. Generated code doesn't send notices, doesn't check a
  password and doesn't remember which notices it handed out: the host drops repeats by id. A stage's `when` in a gate policy is refused
  (MQ8202). Observers, weighted votes and "all", "any" or a share as counts are not offered. Generated code can't tell when an instance that
  was already waiting entered its state, so **Not by** and a round's start miss what was done before the gate got stages.

## 0.19.0 (2026-11-08)

- **Richer sign-off, part 1: approvals.** A gate may now hold **stages**, and a gate with stages is an **approval**. Part 1 allows one
  stage. The stage holds **named signatures**, each with its own `signers`, `required`, `requiredActors` and `allowRepeatSigner`. A signature
  may carry `when`, a condition that says whether it is needed (judged when the object enters the state and again after a rejection; when
  it can't be worked out, the signature is needed), and `notBy`, the verbs and moves whose doer may not give it (counted since the object
  entered the state, including the move that brought it there). One person gives one signature unless the gate sets
  `allowSignerAcrossSignatures`. In the editor, use the Gates tab: **Use named signatures**, **Needed when**, **Not by**.
- **Four responses.** A signer may **sign**, **reject**, **ignore** or **withdraw**. A rejection is a veto: it clears the approval and
  moves nothing, and a move on rejection is an ordinary transition whose verb is `reject`. Ignore finishes that person and leaves the
  count. Withdraw takes back one signature. Rights and trigger points on `reject`, `ignore` and `withdraw` now run at an approval. Two new
  refusals, `gate-excluded` and `gate-not-signed`, and three new audit outcomes, `rejected`, `ignored` and `withdrawn`.
- **Scenarios and simulation.** A step gives a `response` and may name the `signature`. A step may expect `signatures`, the count after
  it (MQ9311). The simulation panel shows each signature: needed, counted, required and who answered. In the engine's rule list, the new
  family "Approvals" (MQ8201, MQ8202) joins the grown MQ9101, MQ9305 and MQ9308.
- **Output.** `csharp-dapper` takes the response and the signature in its envelope, keeps each approval's progress in the snapshot and
  writes a `when` method for each conditional signature. `process-docs` shows the signatures of each approval.
- **A project whose gates use only today's fields is unchanged:** its files, generated bytes, findings, replays and keys. A gate without
  stages takes `sign` only and means what it meant.
- **Upgrading.** Teams upgrade together: an older engine refuses the new keys (`stages`, `allowSignerAcrossSignatures`, a step's
  `response` and `signature`, `expect.signatures`). The schema copies and the `maquettiste-modeling` skill change, so update the copies your
  repository holds. A `csharp-dapper` team with approvals: implement the `when` methods in `<Lifecycle>ApprovalConditions` where the build
  asks (answer true when you can't tell), and pass the envelope's `Response` and `Signature`. The pack's README has the steps.
- **New names.** Settled by the design (section 14): the gate keys `stages` and
  `allowSignerAcrossSignatures`; a stage's `signatures`; a signature's `when` and `notBy`; the part kinds `gate-stage` and
  `named-signature` and the schemas `gateStage` and `namedSignature`; a step's `response` and `signature`; `expect.signatures`; the
  audit outcomes and refusals above, and the audit record's `signature` and `stage`; the gate state's `stages`, the records `GateStage`,
  `NamedSignature`, `ApprovalStageState` and `ApprovalSignatureState`, `GateSignature.signature` and the enabled trigger's `responses`;
  the rule family "Approvals"; the site kind `Approval`, the naming key `ap:approvals`, the index members `approvals` and `signatures`,
  and the template members `model.approval_lifecycles`, `gate.uses_stages`, `gate.all_signatures`, `stage.*` and `signature.*`. In
  `csharp-dapper`: `SignatureResponse`, `ProcessEnvelope.Response` and `.Signature`, `GateDefinition.Stages` and
  `.AllowSignerAcrossSignatures`, `GateOutcome.Rejected`, `.Ignored` and `.Withdrawn`, `Refusals.GateExcluded` and `.GateNotSigned`,
  `GateAuditRecord.Signature` and `.Stage`, `SignatureEntry.Signature` and `.Stage`, `ChartDefinition.RecordsActs`,
  `<Lifecycle>ApprovalConditions`, `ApprovalCall<TContext>` and `IApprovalConditions<TContext>`. In the editor: Use named signatures,
  Back to one list of signers, Needed when, Not by, One person may give several signatures, Response, Signature, Picked by the engine and
  Ignore (abstain). Added while building:
  - Engine: `RNotBy` (kind `not-by`, with `VerbKey`), `RSignatureCount`, `NotByRecord`.
  - `csharp-dapper`: `CommandResult.Approvals`; `ApprovalProgress.Started`, `.Entered`, `.Needed`, `.Signed` and `.Ignored`;
    `ActRecord(Sequence, Signer, Verb, Transition)`; `StageDefinition(Id, Name, Signatures)`; `SignatureDefinition.When`, `.NotByVerbs`
    and `.NotByTransitions`; `EventRequest.Response` and `.Signature`; the `signer` parameter of `Statechart<TContext>.Complete`.
- **Limits.** Generated code can't tell when an instance that was already waiting entered its state, so **Not by** misses what was done
  before the gate got stages. Generated scenario tests don't record verb steps for **Not by**. Part 1 has one stage: rounds, a stage's condition, delegation, reminders, escalation and signing again with a password came in part 2 (0.20.0).

## 0.18.0 (2026-11-08)

- **Trigger points, part 2: named trigger points.** A trigger point may now be its own element, kind `trigger-point`, in
  `model/trigger-points/`. It is for types with no lifecycle (a number on create, an archive on delete) and for one rule shared by many
  types. `subjects` lists the entities and stereotypes it covers, and `exceptEntities` the entities it leaves out. It has the keys of an
  inline point, except `states`, `targets` and `transitions` (MQ8102); read a state with `in_state`. In the editor, use the **Trigger
  points** folder: **Covers**, **Except**, **Never skipped by a bulk load** (`noBypass`) and **Runs for**, the engine's list of the types it
  reaches.
- **The order.** Named points run before a lifecycle's points at each moment. Among them the farthest base comes first; at one depth,
  points that name the type come before points that come through a stereotype, then by name. A named point on a move, signature or task
  verb runs only inside the lifecycle that owns it, for a covered type, never in an orchestration and never in "What happens when" for a
  type alone. Lists of trigger points that name a verb show named points first. A type with no lifecycle gets "What happens when" too.
- **Bulk-load bypass and dry run (`csharp-dapper`).** Both are opt-in through the pack parameters `bulkLoadBypass` and `dryRun`, both off.
  A call may ask to skip optional points; it is honoured only when the team's `TriggerBypass` allows it, every skip is logged, points marked
  `noBypass` still run, and a replace is never skipped. With `bulkLoadBypass` off, `noBypass` has no effect. A dry run stops before the
  effect and records what it would have done. Simulation never bypasses anything.
- **A project that uses part 1 only, or no trigger points, is unchanged:** its files, generated bytes, findings, replays and keys.
- **Upgrading.** Teams upgrade together: an older engine refuses the `trigger-point` kind. The schema copies and the `maquettiste-modeling`
  skill change, so update the copies your repository holds. A `csharp-dapper` team with named points: write the new stubs
  (`TriggerPoints/<Package>/TriggerPoints.cs`). Turn on `bulkLoadBypass` or `dryRun` only if you want them; if you turn on the bypass, write
  `Dispatch/TriggerBypass.cs`, which refuses until you do. Where a process runs a named point that names a type derived from its subject, write `EntityOf` in `<Process>Handlers.cs`; it throws until you do. The
  pack's README has the steps.
- **New names.** Settled by the design: the kind `trigger-point`, `subjects`, `exceptEntities`, `noBypass`, `ITriggerBypass`,
  `Dispatch/TriggerBypass.cs`, `TriggerPointCall.SkipOptional` and `.DryRun`, and the template members `model.trigger_points`,
  `entity.trigger_points`, `trigger_point.no_bypass`, `trigger_point.subjects` and `trigger_point.except_entities`. Added while building,
  settled under the owner's delegation of 2026-11-08:
  - Templates: `trigger_point.package`.
  - Editor API: `GET /api/model/entities/{id}/trigger-sequence` and `GET /api/model/trigger-points/{id}/covers` (`entities`); the records
    `NamedTriggerPointRecord` and `TriggerPointSubjectRecord`; the index rows `subjects` and `subjectStereotypes`; sequence steps gain

## 0.17.0 (2026-11-08)

- **Trigger points, part 1.** A lifecycle may list trigger points: what runs when a verb happens to its objects. A **check** judges the
  change and refuses it with a message (`severity` `error`, the usual choice), or only warns (`warning`). An **action** runs at one moment:
  `before` the checks, to prepare values; `with-change`, in the same unit of work; or `after-commit`, once the change is saved. A
  **replace** takes the place of a built-in effect, on `delete`, `disconnect`, `copy` and `revise` only. In the editor, use the lifecycle's
  **Trigger points** tab, after **Rights**.
- **Where one applies.** Optional keys narrow it to states (`states`), states a move enters (`targets`), moves (`transitions`), types
  (`entities`), attributes (`attributes`) and links (`ends`). A `when` condition says more. A `when`, a check's condition and a set's value
  may read the values before the verb as `old.price`.
- **One fixed order for every verb.** Frozen, rights, guards, signatures, then before actions, checks, the effect (or the replace), actions
  with the change, and actions after commit. A move whose check refuses is left out, as a move whose guard is false is. A check that refuses
  an automatic move leaves it untaken, and the step before it stays accepted. A check that refuses the signature that would complete a
  gate leaves it uncounted, and it is audited as `refused`. An event that names `delete` still does its move, and a replace never stands in
  for it. What a trigger point sets is part of the verb, so rights and freezing judge the actor's own change.
- **What happens when.** The Trigger points tab has a **What happens when** view: pick a verb, and it lists what runs, in order. The MCP tool
  `get_trigger_sequence` and `maquettiste process trigger-sequence <lifecycle> --verb <key>` give the same steps, and `process-docs` writes
  them on the lifecycle's page.
- **Scenarios.** A step's `assume` takes `pass`, `warning` or `error` for a check the team writes, beside the `true` and `false` it takes
  for a guard. A step may expect `checkWarnings` and `triggerPoints` (MQ9310), and a `create` step may give `values`. The refusal `check` is
  new. **Update expectations from replay** and `record_scenario` write the refusal, `refusedBy` and `checkWarnings`, and the trigger
  points only on request (**Also record trigger points**, or `triggerPoints: true`). The simulation panel lists the trigger points that ran.
- **Until generated code can read the object (roadmap 4.6),** a trigger point's `when`, condition and sets go to the team as static methods
  that load the object themselves, as right conditions do. An action written as the team's code fills nothing in a replay, so a check that
  reads those values needs them given on the step.
- **Generated output.** `csharp-dapper` writes trigger point code only when a lifecycle has trigger points: step methods per verb, a static
  method per trigger point for the team, and a runner per type for object, link and own verbs done outside an event. It writes nothing before
  the checks pass, and hands after-commit work to the outbox. `process-docs` adds a Trigger points table and "What happens when" lists. New
  rules MQ8101 to MQ8107 and MQ9310.
- **A project that uses none of this is unchanged:** its files, generated bytes, findings, replays, tool answers and speed.
- **Upgrading.** Teams upgrade together: an older engine refuses `triggerPoints`, `old.` and the new `assume` words. The file format version
  stays 1. The schema copies and the `maquettiste-modeling` skill change, so update the copies your repository holds. A `csharp-dapper` team
  that uses trigger points: write the generated stubs (`<Process>TriggerPoints.cs` and `<Entity>Verbs.cs`, which fail the build until
  written), register `ScenarioTriggers` once in `ScenarioHost` (`TriggerPointStandIn.Current = new ScenarioTriggers();`), call `<Entity>Verbs`
  inside your own transaction for object, link and own verbs, and run a relay that passes each `TriggerPointMessage` from the outbox to
  `TriggerPointRelay.DeliverAsync`. The pack's README has the exact steps.
- **New names.** Besides the names the design lists: in `csharp-dapper`, `ChartDefinition.TriggerSteps` and
  `ChartDefinition.Id`, `TriggerPointWarning`, `TriggerPointDepth`, `StepResult.TriggerPoints`, `CommandResult.TriggerPoints`,
  `StepResult.AfterCommit`, `TriggerPointCall.InState`, `.Enters`, `.MovedBy`, `.Is` and `.Resolves` (written only when rights name actors taken from the object), `ITriggerPointSteps.Speaks` and `.Subject`,
  `TriggerPointOutcome.Ran`, `.Replaced` and `.Messages`, `TriggerPointStandIn` (`Current`, `Check`, `Records`) and `ScenarioTriggers`
  (`Assumed`, `Recorded`). In templates, `trigger_point.team_code`, `trigger_point.covers`, `trigger_point.process` and
  `verb.trigger_points`. In the CLI, `process trigger-sequence`.
- **A limit in generated code.** Generated process code doesn't ask a lifecycle that governs only a derived type of the process's subject.
  Simulation does ask it, and the derived type's own `<Entity>Verbs` runner still runs that lifecycle for a verb step.

## 0.16.0 (2026-11-07)

- **Rights, part 2: freezing.** An object or a link is frozen or not. An accepted `freeze` freezes it and an accepted `thaw` thaws it, whether

  right, and no allow lifts that. A frozen link can't be disconnected or have its attributes modified. Moves, `revise` and the other verbs are
  not stopped, and a move's sets on a frozen object apply, with a note. A right with **While frozen** (`whileFrozen`) holds only while the

  attributes holds, and an allow that names attributes grants nothing. A `read` step may name `attributes`. In **Who can do what**, a cell

  section, says more.
- **New rules.** MQ9309 (warning) for the steps above. MQ9903 now also covers attributes that not every subject holds, attributes beside
  a verb other than `read` and `modify`, and attributes beside links. MQ9305 now also covers `attributes` beside a verb other than `read`.
- **New names.** Each verify result may carry `warnings`, which holds only MQ9309 and is left out when empty. Templates gain
  `right.while_frozen`, `right.attributes`, `step.attributes`, `object.frozen` and `model.freezing.used`.
- **The upgrade.** Teams upgrade together: new files use shapes an older engine cannot read (`whileFrozen`, `attributes` and `frozen`). The file
  format version stays 1. The schema copies and the `maquettiste-modeling` skill change, so update the copies your repository holds. A project

  `csharp-dapper`, `process-docs`, `seed-data`) holds a small `billing-small` case and tests of its helpers. The
  [user guide](user-guide.md#test-a-pack) and the [Share and test packs](guides/share-and-test-packs.md) guide have the
  details.
- **Unit state format 5.** The unit state format moves to version 5, so the first generate after upgrading re-renders
  every unit once.
- **Stereotypes that contribute structure.** A stereotype that applies to tables can carry `columns`, a `primaryKey`,
  `uniques`, `foreignKeys`, `checks` and `indexes`, and every table that carries it inherits them, designed, imported or
  synthesized. An inherited member's id is `<tableKey>.<memberId>`, which seeds, keys, indexes, binding fields and
  queries use like any id. Constraint names come from the naming conventions per table. A member foreign key's target
  is a fixed table or a table each carrier names in a stereotype parameter. A synthesized table that stores a
  stereotype's attributes skips its members, so `audited` keeps serving entities through its attributes. sql-ddl renders
  inherited members as it renders own ones, with no template change. The
  [user guide](user-guide.md#stereotypes-that-contribute-structure) has the details.
- **Default stereotypes.** A database schema entry and a package can list `defaultStereotypes`, applied to every
  element they hold in one line: `{ "name": "billing", "defaultStereotypes": ["audited"] }` gives `audited` to every
  table of schema billing. A default skips the kinds it does not apply to. An element drops a default with
  `excludeStereotypes`. Group, requires and conflict rules judge defaults with the element's own stereotypes, and
  templates read where each stereotype came from in `stereotypes[].source` (`own`, `implied`, `schema-default`,
  `package-default`); `has_stereotype` and `where: { stereotypes: [...] }` see defaults.
- **Exceptions per table.** `excludes` drops inherited members by id, and `redefines` changes a few facets of one
  member (nullable, defaults, comment, collation; a key's columns or name; an index's predicate, method or storage) and
  keeps its id, so the table goes on following the stereotype for everything else.
- **Fold into a stereotype.** The batch operation `fold-into-stereotype` (MCP `apply_batch`, `maquettiste model
  apply`) makes tables that already hold a stereotype's columns, keys and indexes inherit them instead: the own copies
  leave the table files, every reference moves to the keyed ids, differences become `redefines` (with `redefine`) and
  missing members `excludes` (with `excludeMissing`). The write records one `rekey` per database, which now also lists
  the index, unique, foreign-key and check ids it moved, and the next migration holds no statement for it. The [schema
  changes guide](guides/schema-changes.md#fold-columns-into-a-stereotype) explains it.
- Migration facts follow members: renaming a stereotype's column records one complete `rename` for each table that
  carries it and changes no table file; removing one records a `drop` per table. `materialize-tables` keeps inherited
  members inherited and moves the overlay's `redefines`, `excludes` and `excludeStereotypes` into the designed table.
- MCP `get_database_view` and `get_resolved_model` give every inherited column, key, foreign key and index a
  `memberOrigin` (null for own members), and a synthesized table without an overlay now lists the stereotypes defaults
  give it. `get_references` on a stereotype member lists every table and file that names a copy of it, and deleting a
  stereotype lists its member links in the delete plan.
- New rules check members (MQ2024, MQ2025 for a key, index or check naming a column the stereotype lacks, MQ2026 for a
  member foreign key's target), `redefines` (MQ2027, and the warning MQ4078 for a facet equal to the inherited one),
  `excludes` (MQ2028), `excludeStereotypes` (MQ2029, and the warning MQ2030 when it excludes nothing), default lists
  (MQ2031), two primary keys on one table (MQ4076), a refused fold (MQ4077) and a NOT NULL inherited column that rows
  written through an entity cannot fill (MQ4079). MQ2013 now names the schema or package that gives a clashing default.
  MQ4003 also reports a duplicate column name in a synthesized table, MQ4008 suggests the keyed id where a bare member
  id is written, MQ2011 refuses a bare member id under `of: "$element"`, and MQ4106 takes the constraint entries of a
  `rekey`.
- Objects that belong to a package now depend on every package of its chain, so a package that gains a default list
  renders its members' units again. Unit state was already invalidated by the engine version; no output changes.
- **Columns typed by reference types, enums and scalar types.** A table column's `typeRef` names the type whose values
  it holds, beside its `type`, which stays the physical keyword: `"type": "string", "typeRef": { "ref": "<id>" }`.
  Designed, imported, extra and stereotype columns take it. A facet the column leaves out comes from the type, and a
  column typed by a reference type gets what an attribute of that type gets: sql-ddl points it at the bound table or
  the lookup table, or gives it a CHECK (on PostgreSQL a `native` type is a CHECK here), unless the table declares that
  foreign key itself. csharp-dapper reads such a column into a query row as the enum, or as the code's type with a
  summary naming the reference type. `reference_type_usage` lists the columns beside the attributes, templates read
  `column.type_ref`, and `materialize-tables` and `materialize-columns` keep the logical type on the columns they
  write. Typing a column by a type stored as a lookup table, a CHECK, a native type or a bound table records a
  `change-type` that asks how values that are not codes convert. The [reference data
  guide](guides/reference-data-and-seeds.md#11-type-a-column-of-your-own-table) walks through it.
- **Sensitive columns.** A column's `sensitive` (`pii` or `secret`) is said once, on the column or on the attribute a
  binding maps to it, and both sides show it: `attribute.sensitive` and `column.sensitive` now give the borrowed value
  when there is no own one. A column's own `secret` also checks its literal default for credentials (MQ3017).
- New rules check where `typeRef` may sit (MQ4082), that the column can hold the type's values (MQ4083), that a
  declared foreign key from a typed column points at the type's bound table (MQ4084), that the two sides state one
  sensitivity (MQ4085, a warning), and that seed cells, defaults and binding constants written into a typed column are
  its codes (MQ7014).
- **Bindings that record their provenance and drift.** A binding to a designed or imported table now records its
  `provenance`: two short hashes per column, one of the name and one of the type, never a copy of the table and never a
  date. Every materialize operation writes it, and so do the new batch operations `map-by-name` (unmapped attributes to
  free columns of the same name, ignoring case and separators) and `resync-binding`. When the table changes,
  `maquettiste binding drift` and the MCP tool `get_binding_drift` list per binding the columns added, renamed, retyped
  and removed since, from files only; `--check` exits 2 on drift. MQ4087 (a mapped column renamed or retyped) and MQ4088
  (provenance that does not describe the source) join MQ4047, which is unchanged, and all three take the severity
  `validation.rules` gives them. `maquettiste binding resync` (or `resync-binding` through `apply_batch` and
  `preview_materialize`) catches up in one batch: an attribute whose name followed its column takes the new name and
  keeps its id (`--keep-names` keeps every name), a retyped column retypes its attribute unless its type still fits,
  added columns get attributes, and removed columns lose their fields; a refused operation is MQ4089.
  `materialize-entities` and `materialize-attributes` type an attribute by its column's `typeRef`, and a foreign key
  into a reference type's bound table makes no relation. An attribute with no description of its own shows its bound
  column's comment, named by `descriptionColumn` in the resolved model, so when billing's `notes.body` column carries a
  comment, `InvoiceNote.body` is documented with it in generated code. The [bind entities
  guide](guides/bind-entities.md#7-keep-a-binding-in-step-with-its-table) walks through it.
- **Seeds by natural key.** A table seed can list a foreign key of its table in `columns`, in place of the key's own
  columns, and give in each cell the referenced row's natural key: `"ada@example.com"`, or `["ACME", "EU"]` for a key of
  several columns. The engine fills the foreign key's columns with the referenced row's values, so no seed file has to
  repeat a surrogate id. Where the database fills the referenced value, sql-ddl writes a lookup on PostgreSQL,
  `(SELECT id FROM sales.customers WHERE email = 'ada@example.com')`, and inserts rows that look up rows of their own
  table by level; other dialects get `NULL` with a TODO comment (MQ4056), and seed-data lists such cells under
  `unresolved`. Templates read `seed_column.foreign_key` and `data_row.refs`. A natural-key cell is data, not a link:
  deleting the referenced row is not refused, and validation reports the cell (MQ7111).
- **Stable ids.** A `uuid` column the database does not fill can say `"stableId": true`, on a table file or a
  stereotype. Every row the table receives (table seed rows, a bound reference type's rows, entity rows through a
  binding) then gets a UUID version 5 derived from the table's id and the row key, which PostgreSQL's
  `uuid_generate_v5` and most UUID libraries compute the same way, so ids survive rebuilds and agree across
  environments. Templates read `column.stable_id`, and the new helper `stable_id <table> <key>` gives the id of a key;
  `stable_id` is now a reserved helper name (MQ6013). Changing `stableId` or a seed's row key changes the ids of rows
  already in databases.
- **Rows computed by a script.** A seed can take its rows from `rowsFrom: { "script": "seeds/<name>.js" }`, a file
  under `extensions/seeds/` that calls `maquettiste.rows((model, seed) => [...])` once and reads the model as a script
  rule does. Row ids are derived from the seed and the row key, so they are the same on every run. The script runs only
  when something reads its rows, its result is kept until the script, the seed or something it read changes, and a unit
  that read the rows renders again exactly then. The extension file tools write rows scripts (kind `seed-rows`) and load
  them without running them.
- **Seed preview.** `maquettiste seed preview <seed>` and the MCP and assistant tool `preview_seed_rows` (73 MCP tools
  now) give one seed's rows, as written or scripted, or with `--database` (`database`) as that database receives them:
  stable ids, the values natural keys find, and each foreign-key entry's ref. Only the scripts of that seed and of the
  seeds it names run. `seed export` and `export_seed_csv` head a foreign-key column with the foreign key's name and
  write a composite key as JSON array text, and export a scripted seed's rows; `seed import` and `import_seed_csv`
  refuse a scripted seed. The [reference data
  guide](guides/reference-data-and-seeds.md#12-name-a-referenced-row-by-its-natural-key) walks through all three.

  cannot derive the stable id), MQ7126 (a misplaced foreign-key entry), MQ7127 (a rows script that fails) and MQ7128 (a
  scripted row without a row key). MQ7107, MQ7108, MQ7109, MQ7111, MQ7116, MQ5005 and MQ4056 cover foreign-key entries,
  stable id columns and rows scripts too.
- **Rename, retire and merge codes.** Four batch operations change reference data that databases store:
  `rename-code` gives a row a new code, `retire-code` removes a row and moves its uses to another code,
  `merge-reference-types` moves every use of one type to another (mapping codes with `codes`, moving the rows the
  target lacks with their ids and translations) and `rename-reference-type` renames a type. Each goes through MCP
  `apply_batch`, `maquettiste model apply` and the editor's batch endpoint, and a dry run lists what it rewrites
  (`usage`: uses, rows moved and removed, translations removed) and the facts it would record. A merged type's seeds
  whose rows all matched or mapped go with the type. The [reference data
  guide](guides/reference-data-and-seeds.md#15-rename-retire-or-merge-codes) walks through all four on billing's
  invented `PaymentTerm`.
- **Former codes.** A refactor keeps the old code on the type, `formerCodes: [{ "code": "net30", "replacedBy": "<row
  id>" }]`, so a seed import skips a row that names it, `names-to-ids` turns it into the replacing row's id,
  `get_references` on a row lists the former codes that point at it, and templates read
  `reference_type.former_codes`. csharp-dapper writes an `[Obsolete]` field per former code that holds the replacing
  row. A code never comes back: renaming to a live or former code is refused.
- **The value map is recorded and applied.** Each refactor records one `value-map` fact per database that stores the
  type's codes, naming the columns and the template-defined collections that hold them (`collections`, new), the
  merged-away type (`fromReferenceType`, new) and the type's names and plural names (`pluralName`, new in a fact's
  states). On PostgreSQL sql-ddl's migration maps the stored codes before its schema statements: it renames the lookup
  table or enum type of a renamed type, makes the target's rows exist, renames enum values in place where it can,
  maps each column and collection between a drop and a re-add of its foreign key or CHECK, and adds the ledger row; the
  step can run twice. A mapped value an enum type lacks stops the migration with the codes named, since PostgreSQL
  cannot use an enum value in the transaction that adds it. Other dialects get a TODO line. A column whose reference
  type changes without a value map gets its foreign key or CHECK rebuilt (and an enum column its new enum type) on
  PostgreSQL instead of a TODO line. The [schema changes guide](guides/schema-changes.md#codes-that-change) has the
  step per storage strategy. The ledger is unchanged.
- New rules check former codes: a live, repeated or ill-fitting one (MQ7017), a `replacedBy` that is not a row of the
  type (MQ7018), and a default, allowed value or seed cell that names one (MQ7019); MQ7020 refuses a refactor that
  cannot apply. MQ4113 refuses an open value map that maps away a live code, MQ4114 warns when a plain save changes a
  kept row's code or a type's name, and `validate --against` reports such a change that no value map explains
  (MQ4112). MQ4106 and MQ4103 cover value maps.
- **Operations, first cut.** A new kind, `operation`, models one command over the model, in a file under
  `model/operations/` (in a folder per subject): its subject entity (one record or the whole collection, or none),
  whether it reads or changes data, its input members, its outcomes (each completing now or later, and returning
  members, records of an entity or a list of either), its errors (a stable `code`, the name when it has none, and the
  input an error points at), the process events it fires and what it requires. Rules MQ3023 to MQ3028, MQ3030 and MQ3031
  check them. The editor lists operations under their domain and opens them with General and JSON tabs. Templates get
  the scope `each operation` (`type_of` maps a member), and csharp-dapper's new `operation-contracts` unit writes each
  operation's request, result, error codes and handler interface. MCP `get_model_index` rows carry an operation's
  `subject` and `effect`, and `get_resolved_model` has the scope `operations`. An operation screen with grids comes
  later.
- **Operations, second cut.** A stereotype can declare `errors`, and every operation that carries it, or receives it
  from a package's default stereotypes, inherits them by id (`<operation id>.<error id>`); the operation's `excludes`
  drops one and a `redefines` entry changes only its `input`, display name or description, so a shared code stays
  shared. An inherited error takes its stereotype error's translations unless the operation redefines that text, and
  its resolved record carries `memberOrigin`. Removing an error from the stereotype drops the entries that name it.
  A custom property that names the inherited error by its keyed id is cleared in the same save when it is optional
  and reported by MQ2001 when it is required, so the user removes it first, as for a table's inherited column.
  New rule MQ3029 (a stereotype with errors that does not apply to operations); MQ3026 and MQ3027 count inherited
  errors and redefinitions, MQ3026 also reports two stereotypes that give an operation an error of one id, and MQ2027 and MQ2028 judge the operation's `redefines` and `excludes`. Input members can be
  files (`file`, `mediaTypes`, `length` as a byte cap), a `returns` can be a file, and a list can be paged (`paging`
  `page` or `cursor`, with `maxPageSize`); MQ3024 and MQ3025 check both, and `type_of` maps a file member through the
  type map's `file` entry. csharp-dapper maps a file to `System.IO.Stream`, writes a page record and the paging inputs,
  and its new `operation-endpoints` unit writes one ASP.NET Core minimal API route per operation when `endpointsFolder`
  is set (`POST /invoices/{id}/send` for `send` on Invoice), answering 200, 204, 202 or problem details.
- **Custom kinds.** A project can declare kinds of its own, one file each in `extensions/kinds/<type>.json` with a
  display name, a plural name and a JSON Schema per content key; its elements are `kind: "custom"` files under
  `model/custom/<type>/` that hold a `content` object the schema checks (MQ1017, MQ1019, MQ3033). An `x-member` array
  makes each item a member with an id the engine mints, which references (`x-ref` kind `member`, with `of: "$element"`
  for the same element) and translations (`content/<name>` for an `x-translatable` key) can name. Batches name them
  `@custom:<type>.[Pkg.]<name>` and `@member:<type>.[Pkg.]<name>.<member>`. Templates get the scope
  `each custom:<type>` (the variable `custom`) and the helper `custom_named`, and a changed custom kind file renders its
  elements' units again. MCP `get_schema` takes `custom:<type>`, the index, element and kind tools and the CLI's
  `model export` and `model stats` filter by `custom` or `custom:<type>`, and the extension file tools handle custom
  kind files. An operation's `requires` can name a custom element. The editor shows custom elements as JSON for now.
  The [user guide](user-guide.md#custom-kinds-extensionskindsjson) has the details.
- **Calculated values.** A project can define a named value once, in `extensions/calculated/<name>.js`, with
  `maquettiste.calculated({ name, kinds, schema, description, value(element, model) })`: an entity's public name, an
  `apiName`, a label per attribute. Templates read it as `{{ element.calculated.publicName }}` and test for it with the
  new helper `has_calculated`; pack scripts, helpers and other values read `element.calculated.publicName`. Each value
  is evaluated when something first reads it and checked against its schema, so a preview evaluates only the values of
  the objects it reads, and a unit that read a value renders again exactly when that value changes. A rule with `scope:
  "resolved"` checks resolved objects of its kinds, calculated values included, after resolution, in validate and before
  generation plans. `maquettiste model calculated --element <id>` and the MCP and assistant tool `get_calculated` (76
  MCP tools) show the values of the objects named; `get_resolved_model` pages carry them, the template context lists
  them, and the extension file tools handle calculation files and mark resolved rules. New rules MQ5010 to MQ5013 (a
  value that fails, does not fit its schema, is not declared, or reads itself in a cycle); MQ5002, MQ5003 and MQ5005
  also cover calculation files. A project that declares no calculated value pays nothing. Otherwise each value is
  computed once per object of its kinds, in parallel: on the 5,000-entity benchmark, two values on entities add about 36
  ms to `validate`. The editor, the MCP server and `generate --watch` cache values by what they read. The [user
  guide](user-guide.md#calculated-values-extensionscalculatedjs) has the details.
- **Declared rules.** A simple convention no longer needs a script: a file in `extensions/rules/<name>.json` declares
  rules as data, each a selector over resolved objects (`kind`, with `stereotype`, `tag`, `property` or `package`), one
  condition (`all`, `any`, `not`, `has`, `equals`, `count`, `references`, `referencedBy`) and a message with
  placeholders, such as "every audited table has an updated_at column". Declared rules see what generation sees,
  inherited and contributed members included, and run wherever resolved rules run: validate, the editor, the MCP
  `validate` tool and generation; their findings are `x/<id>` and `validation.rules` sets their severity. The extension
  file tools write declaration files in canonical form, check them at once and list their rules; `get_schema` returns
  `declared-rules`. New rules MQ5014 to MQ5017. A project without declaration files pays nothing. The [user
  guide](user-guide.md#declared-rules-extensionsrulesjson) has the details.
- **Suppressions.** An element can accept a finding, with a required reason, in its own file: `suppressions` entries
  name a rule (built-in, script or declared), optionally one part of the element (`member`, an inherited member's keyed
  id included) and the reason. Suppressed findings leave the counts and the report: a suppressed error no longer
  refuses a save or stops generation. `maquettiste validate` prints how many were suppressed, `--format json` lists them
  under `suppressed`, SARIF writes them as results with in-source suppressions and the reason as justification, and

  validate). Every kind schema gains `suppressions`. A project without suppressions pays nothing. The [user

- **Impact before apply.** A batch's dry run (MCP `apply_batch` with `dryRun`, `maquettiste model apply --dry-run`)
  now also answers `impact`: the elements that point at what the change alters or deletes (`referrers`, at most 200
  with `referrersTotal`), the databases it can reach, and per enabled pack the units whose stored inputs it touches,
  with the files they would write again (at most 200 per pack with `unitsTotal`). A unit is `inputs` (a key it read is
  touched), `deleted` (its element goes) or `added` (a created element enters its scope; `filtered` when its `where`
  was not evaluated). A pack never generated here says so (`state: none`). The impact comes from the dry run's own
  models and each pack's stored unit states: nothing is resolved, planned or rendered, so a large model answers as
  fast as a small one, and the impact names the files that would render again, not their new bytes. The text output
  prints a line per referrer, database and unit. [docs/mcp.md](mcp.md#impact) has the details.
- **A model diff for review.** `maquettiste model diff <a> [<b>]` compares two models, each `working`, a model
  snapshot id or a folder that holds another copy of the project (a CI checkout of the base), never a repository. It
  groups the change by package (by qualified name, then "(no package)"), lists each element with its field changes,
  each naming the member it belongs to (attribute `code`, `/name` from `"number"` to `"code"`), and puts the migration
  facts of each database in their own group, labelled by what they record. `--format markdown` prints it for a pull
  request or a hosted change log; `--format json` and `--element <id>` give the comparison and one element's fields.
  The MCP tool `compare_snapshots` now always groups by package, takes a folder in `maquettiste mcp`, and gains
  `fieldChanges` and `format` (`markdown` answers the bytes `model diff` prints). Every field change of a one-element
  comparison, also over HTTP, names its sub-element (`subId`, `subKind`, `subName`, `subPointer`); the HTTP list
  answers as before. The [schema changes guide](guides/schema-changes.md#review-a-change) has the details.
- **Fixes from the milestone D review.** The 37 notes of [issue #2](https://github.com/mattjcowan/maquettiste/issues/2)
  are fixed before release. Those a user can see:
  - On PostgreSQL, a value map that retypes an enum column first drops the views the model knows about, and those the
    migration removes, and creates the model's views again at the end of the migration. A view outside the model needs a
    `raw` fact before and after the step (see the sql-ddl pack's README).
  - A value-map step upserts only the lookup rows it needs, after the rows their fields name, and creates the lookup

  - `list_migrations` and write answers summarize a merge whose codes all match as a merge, and a change of a type's

  - `rename-reference-type` plans only the seeds in the type's own seed folder, so other operations in the batch can
    change the rest.
  - Re-syncing a binding after a column was dropped and added again under the same name moves the attribute to the new
    column instead of adding a second one, also when the re-sync names only some columns.
  - An attribute that shows a bound column's sensitivity or comment is no longer planned again when another entity bound

  - Seed validation follows a lookup through another lookup, as generation does (MQ4056, MQ7125). Outside PostgreSQL,

  - Findings about a default stereotype's parameters name the schema or package instead of its id, and MQ2011 suggests a

  - Changing an enum or reference type re-checks tables that get its typed column through an implied stereotype, and

  expressions of processes lose their 50 ms deadline too, and the 100,000-statement limit alone bounds each one. Before,

- Packs read each other's names. A unit's `exports` states names per element, such as a class name, a namespace or a
  name per attribute; another pack that lists it in `uses` reads them with `exported`, and the unit's own templates read
  them as `exports`. A changed name renders again exactly the files that read it. `maquettiste pack exports` and the MCP

- **One expression language.** A rule about values is written once, in a small typed language that reads like SQL
  (`issuedOn <= dueOn`), and every place where it must hold reads the same text: table and column checks (`condition`,
  beside the SQL text of `expression`), entity checks (the entity's new `checks`, each with the `attribute` a failure
  points at and a `message`), derived values (`derived.value`), process guards (`condition`, beside the JavaScript
  `expression`), operation guards (the operation's new `guards`, each with the `error` it reports) and declared rule
  conditions (`expression`). The new kind `constraint` holds one named condition over typed parameters, which any site
  cites with `satisfies PositiveAmount(amount: total.amount)`. Files hold a tree of ids, printed as text from current
  names, so renaming an attribute or a column never breaks an expression. Every write accepts text in place of a tree
  (`{ "text": "issuedOn <= dueOn" }`: the editor's JSON tab, `save_element`, `create_element`, `patch_element`,
  `apply_batch`, `maquettiste model apply`) and stores the tree; text that does not parse refuses the save, and text
  left in a file by hand converts with the batch operation `text-to-trees` or the Problems fix **Convert expressions to
  trees**. Nulls follow SQL everywhere: a check passes when the answer is unknown, a guard or a rule condition holds
  only when it is true. Integers and decimals are exact, strings compare by code point, times are UTC, and regular
  expressions keep to a portable subset; `float` is not in the language, so its checks stay SQL text. A project that
  writes no expression sees no change. The [user guide](user-guide.md#expressions) and the new [Write a check
  once](guides/expressions.md) guide have the details.
- **Checks in the DDL, guards in simulation.** sql-ddl writes a check held as a tree into the table's DDL on
  PostgreSQL with no template change (`CONSTRAINT ck_invoices_due_after_issue CHECK (issued_on <= due_on)`); on another
  dialect it is left out with MQ4056. An entity check reaches a table only through a binding that lists it in its new
  `checks`, lowered through the field map, and MQ3115 warns about a check a binding could enforce and none lists. A
  schema snapshot keeps a tree check across a rename of a column it reads, so the migration renames the column and
  leaves the check alone. Simulation, scenario replay and `verify_scenarios` evaluate a guard held as a tree, with
  `now()` reading the simulation's clock. Existing JavaScript guards stay as they are: the user guide shows how to
  rewrite one by hand. A corpus of cases runs every operator and function in PostgreSQL and in JavaScript and requires
  the same answers from both.
- **Expressions for tools and packs.** `maquettiste expression preview`, the MCP tool `preview_expression` (77 tools)
  and `POST /api/model/expressions/preview` show an expression's text, type, JavaScript and PostgreSQL text, and with
  a row of values its answer, reading one element only. `get_resolved_model` gives each entity check, derived value,
  guard and constraint condition as `{ text, type, nullable, tree }` (a table check's text is read with a preview) and
  gains the scope `constraints`. Templates read the typed trees
  (`entity.checks`, `check.condition`, `attribute.derived.value`, `guard.condition`, `operation.guards`,
  `model.constraints`); `expression_sql` gives the PostgreSQL text through a binding and `expression_runtime` the
  JavaScript runtime, for packs that write JavaScript. csharp-dapper renders conditions with `expr_cs`, an example
  renderer to copy: an entity with checks gains `Validate()`, one error per failed check at the JSON pointer of its
  attribute, and a guard held as a tree renders from its condition, matching patterns with .NET's linear-time mode.

### Before you upgrade

- **New rules.** MQ3101 to MQ3111 and MQ3113 to MQ3115 check expressions, and MQ4056 also reports a check written in
  the expression language on a database that is not PostgreSQL. A model without expressions reports none of them.
- **Times are UTC.** In the expression language, `date_of`, `date_part` and `add_months` of a `datetimeoffset` work on
  its UTC date and time, and a `datetime` compared with a `datetimeoffset` reads as UTC, so "today" at a guard is the
  UTC date. A project time zone may come later.
- **Three known limits.** PostgreSQL and JavaScript answer the same everywhere but in three cases, listed under
  [Portable rules](user-guide.md#portable-rules) in the user guide.
- **Refresh the schema copies.** The kind schemas gain `checks`, `condition`, `guards` and the `constraint` kind. Run
  `maquettiste init`, or start the editor, which refreshes them; until then `validate` and `generate` warn MQ1008 and
  editors that check files against the copies do not know the new keys.

## 0.11.0 (previews only)

0.11.0 was published only as previews (`0.11.0-preview.1` and `0.11.0-preview.2`); its changes are released in 0.12.0.
Moving from 0.10.1, read this section and the one above.

- **Table seeds follow their foreign keys.** `model.seeds_in_order` puts a table seed after the seeds that hold the
  rows its foreign keys name, in every environment it loads in. A table whose rows name rows of the same table orders
  its seeds, then each seed's rows, so a named row comes first and a seed's rows stay together. sql-ddl follows that
  order, so a seed script may list its blocks, or a self-referencing seed its rows, in a new order. MQ7111 now asks
  for the named row in every environment the row loads in.
- **Reference types stored in a table.** A reference type can name, per database, the table file that holds its rows:
  `bindings` map its fields to columns, and constant columns tell types that share a table apart. Its rows are then the
  table's rows: foreign keys into the table may name them, table seeds may not repeat their keys (MQ7112), and
  `database.seed_tables` lists them first. New rules MQ7117 to MQ7120 check the table, the field map, the key and the
  NOT NULL columns. sql-ddl stores such a type in its table, with no lookup table, CHECK or enum type: `seed.sql`
  writes its rows with the table's other rows, then points every column holding its codes at the table's code column
  with a foreign key. Templates read a column's binding as `column.reference_binding`, and the editor's Storage tab
  gains "Stored in a table".
- **Migration facts.** A change to a database's shape that its stored rows must follow (a rename, a type change, a
  drop, a column made not null) is now recorded as a migration fact: a small file of the new kind `migration` under
  `model/databases/<database>/migrations/open/`, written by the save that makes the change, in the editor, the command
  line, MCP or the HTTP API. Save, create, delete and batch answers list what was recorded (`facts`). A fact that lacks
  what a migration needs (a conversion, a data check, a reason to drop) is pending, MQ4101, and stops generation until
  it is completed or held. `migrations.record: off` in `maquettiste.json` records nothing. The [schema changes
  guide](guides/schema-changes.md) explains each fact and the widening table that decides when a type change needs one.
- **Checking against a baseline.** `maquettiste validate --against <snapshot id or folder>` checks that facts explain
  every change since another copy of the model (a model snapshot, or a folder such as the main line checked out in CI):
  an unexplained change is MQ4102. `maquettiste generate --against` diffs the migrations from that baseline for one run
  instead of the committed physical snapshot, which it leaves alone. MCP `validate` and `plan` take `against`;
  `POST /api/validate?against=` and `POST /api/generate/plan` take a snapshot id.
- **Listing and folding facts.** `maquettiste migration list` and the `list_migrations` tool (also the assistant's)
  list the open facts in the order they apply. `maquettiste migration fold` and the `fold_migrations` tool remove stale
  facts (MQ4103: a change made and undone) and join consecutive ones; fold facts this way, never delete their files by
  hand.
- New rules MQ4101 to MQ4111 (the new "Migrations" family) check facts: missing intent, unexplained or stale changes,
  `after` links in a cycle, to another database or to nothing, fields that do not fit the fact, two facts on one object
  with no order, SQL text without the database's dialect, a baseline with errors, and a write that recorded nothing for
  elements with errors. MQ4056 also reports migration facts outside PostgreSQL.
- **sql-ddl migrations apply facts.** On PostgreSQL a fact's step replaces the TODO a migration wrote before: a rename,
  a type change with its data check and conversion, a backfill before `SET NOT NULL`, a drop, a raw step behind its
  guard; a held fact waits for its release, and on every dialect a held drop or rename writes a note instead of the
  drop or rename. Migrations are now named `<NNNN>-<key>.sql` (`<key>.sql` with `--against`), the key hashing their
  content, and open with their from state, to state and facts, so the migrations of copies that diverged get distinct
  names and chain by state. Migrations named `0001.sql`, … earlier keep their names.
- **Earlier migrations stay yours.** A migration (any `once` file) of a pack that still exists stays tracked while it is
  on disk, even when no run produces it, so the pack no longer renders placeholders for earlier revisions and
  `generate --check` never reports them.
- `get_project`'s workspace (the branch) is now read by the MCP server and the editor's assistant once, when they start:
  restart the server after switching branches. The engine itself reads no version control.
- **The migration ledger, version 1.** On PostgreSQL, the sql-ddl scripts record the migration facts they reach
  in three bookkeeping tables, in the schema `migrations.ledgerSchema` names (default `migration_ledger`), inside the
  script's own transaction. `maquettiste migration ledger --grant-read <role>` and the `get_ledger_ddl` tool print the
  DDL and the read grant for a team's own migrator. [The migration ledger](ledger.md) has the contract, frozen at
  version 1: a change to it is version 2, with a conversion in its DDL. New rule MQ4067 (a warning): the ledger schema
  is also a schema of the database's modeled objects.
- New built-in helper name: `ledger_ddl`. A pack helper of that name is now MQ6013; rename it.
- **Range columns.** A column can be a `range` or `multirange` with a `subtype` (PostgreSQL's built-in range types);
  sql-ddl migrates between them with the cast PostgreSQL has, and csharp-dapper holds them as text. Elsewhere they are
  stored as text.
- **Index nulls.** An index column can sort its nulls `first` or `last` (PostgreSQL).
- **SQL object environments and run-once.** A SQL object can list the `environments` it runs in: sql-ddl writes it only
  to `objects.<env>.sql`, which runs on every deploy, so its statements must be safe to run again. `apply: once` runs a
  SQL object one time per database behind a migration ledger guard that records it (PostgreSQL). New rules MQ4069 (a
  dependency that does not run in every environment its dependent runs in) and MQ4070 (environments with phase
  `before`). A `rekey` migration fact can list a SQL object whose id changed.
- **Name rules.** Two index or constraint names that collide where the dialect keeps one namespace for them are now
  MQ4068 (error): two indexes on the same columns that both take the conventional name, an index named like a key or a
  table on PostgreSQL, a foreign key name used twice in a MySQL schema. Names compare without case after cutting to the
  identifier limit. The over-long name check (MQ4001) on conventional names now counts UTF-8 bytes on PostgreSQL and
  Oracle, as it already did on given names; a name with letters outside ASCII may now be reported.
- **Column defaults.** A column's literal default is checked against its resolved length (the conventions'
  `defaultStringLength` when the column has none). A `json` column's default must be a string of JSON text: an object,
  array, number or boolean, which the DDL could not write, is now MQ3019; use a string or `defaultSql`. A column with a
  `nativeType` is checked for the kind of value only.
- **Batches by name.** A batch (MCP `apply_batch`, the new `maquettiste model apply <batch.json>`, the editor's
  assistant) can name what it touches instead of carrying ids: `@kind:path` with the names as written in the files
  (`@table:billing.notes`, `@entity:Billing.Invoice`, `@column:billing.notes.body`), and placeholders declared with
  `"as": "$name"` for elements the same batch creates. The engine mints every missing id, a sub-element's included, and
  the answer lists the names it resolved and the ids it minted (`ids`). Files stay id-based. `apply_batch` takes
  `dryRun`, and `model apply` takes `--dry-run`: nothing is written, and the answer has a unified diff per file and the
  diagnostics the change would add and remove. New rules MQ1012 to MQ1015 (a name that finds nothing, a name that finds
  several, a misused identity, a malformed or misplaced name); an update that drops a sub-element and adds a same-named
  one without its id is refused (MQ1014: keep its id). See [batches by name](mcp.md#batches-by-name).
- The assistant's proposals resolve names the same way and no longer retry to fill in missing ids; each proposed file
  carries its diff (`diff` on `AssistProposalFile`). `BatchResult` gains `ids`, and `BatchOperation` gains `as`.
- **Typed links in custom properties.** A property schema (an extension file, a stereotype's `parameters`, a pack's
  `parameterSchema`) can type a value as the id of an element or sub-element with `x-ref`: `kind`, `of` (`$element` for
  a member of the holder, or an element whose seed rows it names), `sameDatabase` and `optional`. Validation checks the
  values (MQ2010: a name where the id belongs; MQ2011: a target out of scope; MQ2009: a malformed `x-ref`), deletes and
  saves treat them as references (cleared by `remove-references` when optional), and `get_references` rows carry
  `optional` and `schema`. The batch operation `names-to-ids` turns the values still written as names into ids, for the
  whole model or the `elementIds` given.
- **Stereotype rules and parameters.** A stereotype can declare a `group` (one per element), `requires`, `conflicts`
  and `implies` (one level), and typed `parameters` for the custom properties of the elements that carry it. Implied
  stereotypes act as listed ones, and templates see them with `implied_by`. New rules MQ2013 to MQ2019; MCP
  `get_schema` returns `stereotypeParameters`.
- **Packages on every kind, and layers.** Tables, views, sequences, routines, database types, SQL objects, queries,
  databases, mappings, stereotypes, reference types, seeds, actors and scenarios can join a package (`package`), which
  groups them without changing any database. A package's `dependsOn` lists the packages its elements may reference;
  any other reference from a checked package is MQ2020, and a `dependsOn` that names its own package or forms a cycle
  is MQ2021. A model without `dependsOn` behaves as before. The seeds of one target merge in a fixed order, and two
  seeds of one table that key their rows differently are MQ7121.
- **Translatable custom properties.** `"x-translatable": true` on a top-level string property of an extension file or
  of stereotype parameters makes its text translatable per locale, as the field `properties/<name>` in the translation
  screens, `get_translations`, `set_translations`, `localization_status`, the `l10n` verbs and their exports; templates
  read it with `translate(entity, "properties/<name>")`. New rules MQ7212 (a misplaced keyword) and MQ7213 (a keyword
  on kinds that have no translations).
- **Tags into a property.** The batch operation `tags-to-property` moves the tags that start with a prefix
  (`status:draft`) into a custom property (`status`), converted by the schema that declares it, and removes them from
  the vocabulary.
- **Rationale, decision and status.** Every element, attribute, enum member, column, database schema and category can
  carry `rationale` (Markdown), `decision` (a URL or a decision record reference) and `status` (`proposed`,
  `approved`, `deprecated`, `retired`). A reference to a retired element is MQ2022, a warning, so retiring something
  lists its last users. Templates read the three fields on entities, tables, databases and most other resolved
  elements; editing them records no migration fact.
- The editor's forms do not show the new keys yet: edit them on the inspector's **JSON** tab. The new guide [Typed
  properties and layers](guides/typed-properties-and-layers.md) walks through all of them, and the modeling skill
  (`maquettiste init --skill` refreshes it) teaches agents to use them.
- **Seeds by name in templates.** `seed_named "currencies"` finds a seed by its name (`Billing.currencies` when its
  file states a package), so a template can write one constant per row of one seed without looping over every seed;
  a name two seeds share fails the unit (MQ6006). Renaming a seed into or out of the name renders the unit again.
  `seed_row <seed> <key>` finds one row by the code of a reference type's seed, the row key of a table seed or the key
  of an entity's seed. Templates read a seed's longest name as `qualified_name`. New built-in helper names: a pack
  helper named `seed_named` or `seed_row` is now MQ6013; rename it.
- **Seed columns and cells by name.** A seed written through `create_element`, `save_element`, `patch_element`,
  `apply_batch`, `model apply` or the editor's API may give its `columns` and `key` by name and a row's cells as a
  `values` object keyed by its columns; the file still stores ids and one cell per column. A name that finds nothing or
  several is MQ1002 and nothing is written. See [seeds by name](mcp.md#seeds-by-name).
- **Closed block comments.** A `block` unit can set `blockCommentEnd`, the text that ends each delimiter line, so a
  managed block fits a file whose comments must be closed: `<!--` and `-->` in an XML or HTML file. A delimiter line is
  found whatever its comment and closing text, and other closing text is rewritten on the next run. See [managed
  blocks](user-guide.md#managed-blocks-a-few-generated-lines-in-a-file-you-own).
- **Copy units.** A unit in the new mode `copy` names no template: its `sources` (glob patterns over the pack's files,
  matched case-sensitively) are copied under its `output` folder, each after the pattern's fixed folders. `tokens` maps
  literal text to a pack parameter, so a skeleton stays code that builds: `"Skeleton.Api": "rootNamespace"` writes the
  project's namespace into every text file and path. Text files change only where a token occurs (line endings and
  every other byte stay, no formatter runs); other files, such as images, are copied byte for byte. The copies are
  managed like overwrite files: a changed, added or removed source renders the unit again, and a hand edit is MQ6009. A
  pattern that matches no pack file is MQ6030 and a token whose parameter is undeclared or not a string is MQ6031;
  either skips the unit while the pack's other units render. The preview lists every copied file and marks binary ones
  (`binary: true`, no text), a binary file's diff reads `Binary file <path> differs`, and the editor's file list marks
  the files a copy unit copies as `copy-source`; they are never parsed, loaded as pack scripts or read as type maps. See
  [copy units](user-guide.md#copy-units-a-folder-of-files-copied-as-they-are).
- **Template helpers that find and order.** `table_named "billing.invoices"` finds a table by name in every database (or
  the one you pass), `column_named` one of its columns; renaming a table into or out of the name renders the unit again,
  and a name two tables share fails the unit (MQ6006). `array_index_of` and `array_find` search a list by an item's
  member, `toposort` orders a list by `[before, after]` pairs (stable; a cycle releases the earliest item left), and
  `json` takes member paths, `json table ["name", "columns.name"]`, so a table or entity can be written as JSON.
- **Two scopes.** `each database` runs a unit once per database, without a selector script; `each attribute` once per
  attribute declared in a model file (never an inherited or added copy). Their `where` filters as the user guide says.
  The example packs' database units (sql-ddl's schema, migration, seed and environment scripts, seed-data's data) now
  use `each database`, and their scripts no longer register a `databases` selector; unit keys and outputs are unchanged.
- **Definitions on `model`.** `model.stereotypes`, `model.tag_vocabularies` and `model.category_trees` list the
  stereotypes (with the attributes they add and their default properties), the tag vocabularies and the category trees.
  A category now also has `parent`, `children`, `order` and `description`.
- New built-in names: the helpers `array_index_of`, `array_find`, `table_named`, `column_named` and `toposort`, and the
  template variables `database` and `attribute`. A pack helper with one of these names is now MQ6013; rename it.
- **Absent values are null.** A value a model file leaves out reads as null in templates, pack scripts and
  `get_resolved_model`, never as an empty text: the display and plural names of tables, columns and other database
  objects without them, the `body` of a view, routine or SQL object without text for the database's dialect, the
  `returns.native_type` of a routine that returns a table, the `native_name` of a database type the dialect cannot
  create, the `sql` of a query that cannot be written for the dialect (and of a nested query), and the `description` of
  a gate's audit field. A template that compares one of these with `""` should compare with `null`; sql-ddl now does.
  Values that are worked out keep their rule (an element's display name falls back to its name). `display_name`,
  `plural_name` and `description_of` give a database object's own text. csharp-dapper's audit records now describe an
  audit attribute without a description as `Audit attribute <name>.` instead of leaving the summary empty.
- **Plain helpers.** `maquettiste.helper(name, fn, { plain: true })` gives a pack helper frozen plain copies of its
  arguments instead of read-only views, which are faster to read in a loop. A copy reaches two hops: a table argument
  has its columns and its database, and what they hold is `{ id, kind }`. Everything copied counts as read. A copy has
  no `hasStereotype`, `hasTag` or `find`, and the model itself cannot be passed; any other option stops the script from
  loading (MQ6016).
- **Scoped generation.** `maquettiste generate --element <id>` and `--unit <pack>/<unit>` (both repeatable; values of
  one option OR, the two options AND) run only those units: their files are written, their outputs that are no longer
  produced are deleted, and every other file and unit record stays as the last run left it, so the next full run
  writes the rest. `--unit sql-ddl/schema --element <database id>` regenerates one database's schema script. A limited
  run never moves the schema snapshots, so a selected unit that reads the schema difference (`sql-ddl/migration`)
  fails with MQ6033; migrations render only in a full run. New rules MQ6032 (a unit filter that names a pack the run
  lacks, a unit no run pack has, or a unit id several run packs have) and MQ6034 (a warning: the filters select
  nothing). MCP `plan` and `generate` take `units` and `elements`, and so does `POST /api/generate/plan` in its body;
  a limited plan's apply writes only its own units' files. See [regenerate one element or one
  unit](user-guide.md#regenerate-one-element-or-one-unit).
- **Short answers for agents.** Three MCP tools answer a summary first, so an agent's first calls stay small on a large
  model. `get_project` names the packs with their unit counts, counts the pack diagnostics and names the extensions;
  `sections` (`settings`, `packs`, `extensions`) adds the typed settings, the pack manifests and diagnostics, or the
  extension schemas, which the answer no longer carries by default (`packs` and `extensions` now hold the summaries and
  the names), and the always-empty `git` member is gone.
  `list_validation_rules` with no argument answers the rule families with their counts; `family`, `ids` or `query`
  answer full entries in pages. `tag_usage` answers each tag with its use count and a few element names; `tag` answers
  the ids of the elements that hold one tag, in pages. The editor's HTTP routes answer as before. The assistant's
  `get_project`, `list_validation_rules` and `tag_usage` answer the same summaries. See [reading a large
  model](mcp.md#reading-a-large-model).
- **Patches.** The new MCP tool `patch_element` changes part of one element with an RFC 6902 JSON Patch and the hash
  the caller read, instead of the whole document: the same conflict check, validation and migration facts as
  `save_element`, and the engine mints the id of a new sub-element sent without one. A patch that cannot be applied (an
  unknown operation, a path that does not resolve, a failed `test`, a change to `/id` or `/kind`) is the new rule
  MQ1016, and nothing is written.
- **Generate in one call.** The new MCP tool `generate` renders and writes in one run, as `maquettiste generate` does,
  and answers a summary per pack: counts by kind, the first 50 paths, and at most 100 diagnostics, errors first. No
  plan is stored. `plan`, `get_plan_diff` and `apply_plan` remain for a review before writing. The MCP server now has
  71 tools.
- **Script limits without the clock.** `limits.scriptTimeoutMs: 0` in `maquettiste.json` turns the scripts' wall clock
  off, so script rules and pack scripts give the same results on a busy machine as on a quiet one; the statement limit
  and the memory limit (`limits.scriptMemoryBytes`, every byte a call allocates) then bound each call. Use it in CI. A
  regular expression match keeps its 250 ms bound, and previews and path listings keep a deadline of 8 seconds. `limits.scriptStatements` is now at most 2,000,000,000.
- **A scope per rule file.** Each file in `extensions/rules/` now runs in its own function scope, and the globals are
  frozen before the rule files run. A rule can no longer call a function of another rule file, and a rule file that sets
  a global or adds to a built-in prototype fails to load with MQ5002: copy a shared function into each file that needs
  it. Pack scripts are unchanged. New rule MQ5005 (a warning): a rule file declares `let` or `var` at its top level,
  state a rule must not keep between calls; `validate` and the Extensions tab show it.
- **Whole-model rules.** `maquettiste.rule({ id, severity, scope: "model", check(model, report) })` checks the model
  once per full validation instead of once per element, such as "every reference type is used"; each `report` names the
  `element` its finding is about. Element saves do not run it. `list_extension_files` marks such rules `wholeModel`.
- **Faster script rules.** A rule's `model` gains `withStereotype(key)`, `withTag(tag)`, `withProperty(key)` and
  `byQualifiedName(name)` (the qualified names batches take), backed by indexes built once per model, and
  `model.all(kind)` no longer scans every file. The editor, the MCP server and `generate --watch` keep each rule's
  findings per element in memory and run a rule again only on the elements whose inputs changed.

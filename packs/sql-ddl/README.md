# sql-ddl

SQL DDL for **PostgreSQL**, **SQL Server** and **SQLite** from the resolved physical model: one script per table, one schema
script per database, migrations written once from the schema diff, and a seed script with a protected region. MySQL and Oracle
databases get portable SQL without dialect-specific clauses.

The pack writes to a **committed** output root. `maquettiste init --pack sql-ddl` sets `packs.sql-ddl.output` to `db` and
declares `db` with `commit: true`, so every path below is under `db/`.

## Output

For a database `main` (PostgreSQL, schema `billing`) with a table `invoices`:

| Unit | Mode | For | Writes |
| --- | --- | --- | --- |
| `table` | `overwrite` | `each table` | `main/billing/tables/invoices.sql`: `CREATE TABLE` with columns, primary key, unique constraints, foreign keys and checks, then its indexes and comments |
| `schema` | `overwrite` | `select databases` | `main/schema.sql`: schemas, sequences, every table in foreign-key dependency order, then views |
| `migration` | `once` | `select databases` | `main/migrations/0001.sql`, `0002.sql`, …: one script per schema revision, from `schema_diff` |
| `seed` | `regions` | `select databases` | `main/seed.sql`: lookup-table rows as idempotent upserts, plus a `seed-data` region the team fills in |

Database folders are the kebab-case database name; the schema folder is left out when the table has no schema (SQLite).

## What the DDL covers

- **Columns**: the dialect's native type (`type_of column "<dialect>"`, so `typeMaps` overrides and `nativeType` overlays apply),
  `NOT NULL`/`NULL`, collation, defaults (per-dialect `defaultSql`, then a literal through `sql_literal`, then the key
  sequence, then the attribute's `defaultExpression`: `now`, `today`, `new-uuid`), identity (`GENERATED BY DEFAULT AS IDENTITY`,
  `IDENTITY(1,1)`, or SQLite's `INTEGER PRIMARY KEY` rowid alias) and computed columns. SQL Server defaults are named
  `df_<table>_<column>` so migrations can find them: a migration drops the default before it drops or alters the column, and
  renames it with its column or table.
- **Constraints**: `CONSTRAINT <name> PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY … REFERENCES … ON DELETE/ON UPDATE` (SQL Server has no
  `RESTRICT`; `NO ACTION` behaves the same there) and `CHECK` with the dialect's expression.
- **Indexes**: unique, descending columns, `INCLUDE` (PostgreSQL, SQL Server), partial `WHERE`, `USING btree|hash|gin|gist`
  (PostgreSQL) and clustered (SQL Server `CLUSTERED`, with the primary key made `NONCLUSTERED`; PostgreSQL `CLUSTER … USING`).
- **Comments**: `COMMENT ON` (PostgreSQL), `sp_addextendedproperty` `MS_Description` (SQL Server), trailing `--` comments (SQLite).
- **Schemas, sequences and views** (schema script): `CREATE SCHEMA` for every schema but `public`/`dbo`, `CREATE SEQUENCE` (none
  on SQLite), `CREATE VIEW` with the dialect's body. SQL Server statements are separated by `GO`.

Identifiers are quoted with `sql_quote` according to the database's `quoting` setting (or the `quoting` parameter).

## Migrations

The pack sets `usesSchemaDiff`, so the engine keeps `.maquettiste/snapshots/<database>.json` and gives templates the difference
between that snapshot and the current model as `schema_diff.<database>`. A generate that changes the physical model writes
`migrations/<revision>.sql` once (mode `once`) and advances the snapshot. The first migration creates everything; later ones hold
`ADD`/`DROP`/`RENAME COLUMN`, type, nullability and default changes, constraint and index changes, table and view renames, and
sequence changes, in one transaction. Statements run in phases so nothing is used before it exists: table renames, then
constraint and index drops and renames (foreign keys first), then dropped tables, then column changes, then new tables, then new
and changed constraints and indexes (foreign keys last). A changed constraint or index is dropped in the first phase and created
again in the last. When a lookup table changes (an enum member was added or renamed), the migration upserts its rows the way
`seed.sql` does; rows of removed members are left in place. What a diff cannot decide is written as a `-- TODO` line: data conversions, SQLite's
missing `ALTER COLUMN` and `ADD CONSTRAINT` (rebuild the table), a new `NOT NULL` column without a default.

Migrations are yours once written: review them, edit them and commit them; the engine never overwrites them. Each run also
re-emits every earlier revision as a short placeholder; because an existing `once` file is always kept, the placeholder is only
written if you delete a migration, and it keeps the committed migrations owned by the pack, so `generate --check` does not report
them as orphaned after the snapshot has moved on.

A dropped table, view or sequence is named with the database's default schema (the diff records only the old name).

## Seed data and protected regions

`seed.sql` is regenerated on every run (lookup rows for enums stored as `lookup`, written as upserts: `INSERT … ON CONFLICT (id)
DO UPDATE` on PostgreSQL and SQLite, `MERGE` on SQL Server, so the script can run again on a database that has them), but
everything between

```sql
-- maquettiste:keep id=seed-data
-- maquettiste:end-keep
```

is carried over from the file on disk. Edits outside the region are reported as hand edits. `regions` mode only works on a
committed root.

## Parameters

Set them in `maquettiste.json` under `packs.sql-ddl.parameters`.

| Parameter | Default | Meaning |
| --- | --- | --- |
| `comments` | `true` | Emit table and column comments. |
| `quoting` | `""` | `always`, `reserved` or `never` to override every database's `quoting` setting; empty keeps the database's. |
| `schemaScript` | `"inline"` | `inline` puts every table's DDL in `schema.sql` (runs with any client); `include` writes client include directives instead (`\ir` for psql, `:r` for sqlcmd followed by `GO`, `.read` for sqlite3; paths use `/`, which sqlcmd accepts on every OS; run sqlcmd and sqlite3 from the database folder). |

## Files

| File | Holds |
| --- | --- |
| `pack.json` | Units and parameter defaults. |
| `helpers.js` | The `databases` selector and the `ddl_order` / `ddl_cycle_breaks` helpers (foreign-key dependency order). |
| `_sql.scriban` | Shared functions: quoting, qualified names, column definitions, foreign keys, indexes, comments. |
| `_table.scriban` | The `CREATE TABLE` block of one table, used by `table`, `schema` and `migration`. |
| `_objects.scriban` | Sequences, views, schemas, include directives and the dependency spec for `ddl_order`. |
| `_migration.scriban` | Statement builders over the schema diff. |
| `table.scriban`, `schema.scriban`, `migration.scriban`, `seed.scriban` | The unit templates. |

## Notes

- Tables in a foreign-key cycle cannot all be created with their constraints in place on PostgreSQL and SQL Server. The schema
  script and the first migration leave the constraints that point forward out of their `CREATE TABLE` and add them with
  `ALTER TABLE … ADD CONSTRAINT` after the last table; in `include` mode a table holding such a constraint is written inline,
  because its table script declares every foreign key. SQLite accepts forward references and keeps them inline. The per-table
  scripts always declare every foreign key.
- Templates build text with string concatenation and append to lists in place (`list[list.size] = x`) instead of `array.add`:
  Scriban counts every element an array function copies against `limits.templateLoopLimit`, and a schema script or first
  migration renders every table of a database in one unit. Databases with tens of thousands of tables may still need a higher
  `limits.templateLoopLimit`.
- The model is walked from the templates, not from JavaScript: `ddl_order` receives the foreign-key graph as a compact string,
  because reading thousands of model objects through the sandbox's proxies exceeds the script time limit.
